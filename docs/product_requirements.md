# Texas Holdem Online 产品需求文档

## 1. 文档目标

本文档以当前仓库已有实现为基础，重新整理本阶段的真实需求边界、玩法流程、客户端交互要求和验收标准。目标不是描述一个“未来可能做成什么样”的完整产品，而是明确这一版必须稳定交付什么，以及哪些能力仍属于后续迭代。

本阶段的交付目标是：

- 提供一个基于 Python 的 gRPC 服务端和 `pygame` 客户端。
- 支持 2 到 6 名玩家在同一房间内完成一手完整的无限注德州扑克。
- 牌局可以从“进入房间/入座/准备”推进到“发牌/下注/摊牌/结算/展示结果/重置桌面”。
- 服务端负责权威规则计算，客户端负责清晰展示状态并限制明显非法的交互入口。

## 2. 当前范围

### 2.1 本阶段必须完成的能力

- 单房间联机牌桌。
- 玩家加入房间、入座、离座、准备、开局。
- 自动开局倒计时。
- 服务端发牌、盲注扣除、行动顺序推进。
- `FOLD`、`CHECK`、`CALL`、`RAISE`、`ALL_IN` 五种行动。
- Flop / Turn / River / Showdown / Hand Complete 全流程推进。
- 提前弃牌胜出、摊牌比牌、主池与边池结算。
- 客户端展示公共牌、自己的手牌、底池、当前下注、最小加注、最近日志和上一手结果。
- 自动化测试覆盖服务端规则与客户端核心交互逻辑。

### 2.2 明确不在本阶段验收范围内的能力

- 账号系统、好友、匹配大厅、排行榜、商城。
- 真金货币、充值、提现。
- 完整的断线恢复 UX 和离线保座策略。
- 行动倒计时惩罚和超时自动操作。
- 聊天内容审核、历史消息持久化。
- 多房间管理后台或运营工具。

说明：

- `proto` 和服务端中已经预留了 `heartbeat`、`reconnect`、`chat_message` 等消息形态，但这些能力在当前版本只算“协议预留/基础接线”，不作为本阶段完整验收项。

## 3. 用户角色

### 3.1 玩家

玩家通过客户端连接服务器，加入固定房间，选择空座位，准备后参与牌局。

玩家需要能够：

- 输入服务器地址和昵称。
- 进入房间后看到座位状态和牌桌状态。
- 选择空位入座或主动离座。
- 在等待阶段切换准备状态。
- 在自己回合执行合法动作。
- 在手牌结束后看到赢家、筹码变化和上一手结果。

### 3.2 服务端

服务端不是用户，但它是权威裁判，必须：

- 维护房间、座位和手牌状态。
- 负责洗牌、发牌、行动合法性校验、阶段推进和结算。
- 只向对应玩家下发自己的私有手牌。
- 向所有订阅者广播公开快照。

## 4. 端到端业务流程

### 4.1 连接与进房

流程：

1. 玩家在客户端输入服务器地址和昵称。
2. 客户端建立 gRPC 双向流连接。
3. 客户端发送 `JoinRoom`，默认进入 `lobby`。
4. 服务端返回 `Joined` 事件，分配 `player_id` 和 `reconnect_token`。
5. 服务端广播 `RoomSnapshot`。

验收要求：

- 未连接前客户端显示未连接状态。
- 连接成功后客户端显示已进入房间。
- 同一房间内多个客户端能看到一致的公开快照。

### 4.2 入座与准备

流程：

1. 玩家点击空座位发送 `SitDown`。
2. 已入座玩家可切换 `SetReady(true/false)`。
3. 服务端维护座位占用、准备状态和基础筹码。

验收要求：

- 玩家不能重复占用多个座位。
- 已被占用的座位不可再入座。
- 筹码为 0 的玩家不能进入准备状态。
- 准备状态变化会同步给所有客户端。

### 4.3 自动开局

流程：

1. 等待阶段中，至少两名入座且准备完成的玩家存在时，服务端开始倒计时。
2. 倒计时结束自动开始新手牌。
3. 若准备人数重新低于两人，则倒计时取消。

验收要求：

- 倒计时秒数出现在 `RoomSnapshot.auto_start_countdown_seconds`。
- 客户端桌面顶部能显示倒计时文案。
- 玩家人数不足时不能开局。

### 4.4 开局与发牌

流程：

1. 服务端轮转庄位。
2. 两人局下，庄家同时承担小盲并在翻牌前先行动。
3. 多人局下，庄家左侧依次为小盲和大盲。
4. 服务端扣除盲注并向活跃玩家发两张手牌。
5. 服务端设置当前行动位、当前下注和最小加注。

验收要求：

- 小盲和大盲扣款正确。
- `dealer_seat`、`active_seat`、`current_bet`、`min_raise` 正确下发。
- 客户端只展示自己的两张手牌，其他玩家只显示手牌数量。

### 4.5 下注轮与交互约束

支持动作：

- `FOLD`
- `CHECK`
- `CALL`
- `RAISE`
- `ALL_IN`

服务端规则要求：

- 只能由当前行动位玩家操作。
- 面对下注时不能 `CHECK`。
- `RAISE` 目标额不能低于 `current_bet + min_raise`。
- `RAISE` 目标额不能高于玩家可用筹码形成的总下注额。
- 短码 `ALL_IN` 如果未构成完整加注，不得错误缩小 `min_raise`。
- 所有可行动玩家完成动作且投入对齐后，牌局才进入下一街。

客户端交互要求：

- 只有轮到自己时才显示可操作入口。
- 客户端必须按快照禁用明显非法动作：
  - 面对下注时禁用“过牌”，启用“跟注”。
  - 不面对下注时启用“过牌”，禁用“跟注”。
  - 无法达到最小加注额时禁用“加注”。
  - 仍有剩余筹码时允许“全下”。
- 即使客户端做了禁用控制，服务端仍是最终裁判。

### 4.6 公共牌推进

流程：

1. Preflop 完成后发 3 张 Flop。
2. Flop 完成后发 1 张 Turn。
3. Turn 完成后发 1 张 River。
4. River 完成后进入 Showdown。

验收要求：

- 公共牌数量按 `0 -> 3 -> 4 -> 5` 推进。
- 街道推进前，当前街的下注必须已完成。
- 所有人都已全下时，服务端自动发完剩余公共牌并结算。

### 4.7 提前胜出

流程：

1. 任一时刻如果只剩一名未弃牌玩家。
2. 服务端直接将全部底池判给该玩家。
3. 本手进入 `HAND_COMPLETE`。

验收要求：

- 不进入摊牌比较。
- 赢家获得全部底池。
- `last_hand_result` / `last_hand_summary` 中保留本手结果。

### 4.8 摊牌与结算

流程：

1. River 下注完成后进入 Showdown。
2. 服务端从每名存活玩家的 2 张手牌和 5 张公共牌中选出最佳 5 张牌。
3. 比较牌型与踢脚。
4. 依据每名玩家的总投入拆分主池和边池。
5. 仅允许有资格的玩家争夺对应底池。
6. 平分时按顺序分配余数，保证总筹码守恒。

验收要求：

- 支持标准德州扑克牌型。
- 支持 A-2-3-4-5 轮顺。
- 同牌型时由踢脚正确比较。
- 弃牌玩家保留历史投入，但绝不能赢得任何底池。
- 边池资格正确，短码玩家不能赢取自己未覆盖的筹码。

### 4.9 手牌结束与结果展示

流程：

1. 结算完成后牌局进入 `HAND_COMPLETE`。
2. 服务端生成 `HandResult` 与房间内的上一手摘要。
3. 客户端在侧边栏显示上一手赢家、手局 ID 和筹码变化。
4. 短暂停留后桌面重置回等待阶段。

验收要求：

- `HandResult` 包含：`hand_id`、`hand_number`、`board`、`pot_awards`、`winner_seats`、`shown_hands`、`chip_deltas`。
- 客户端在结果展示阶段不崩溃、不丢失上一手结果。
- 重置后可以继续等待下一手。

## 5. 协议与状态要求

当前 `proto/poker.proto` 中，本阶段实际依赖的消息包括：

- ClientEvent:
  - `JoinRoom`
  - `SitDown`
  - `StandUp`
  - `SetReady`
  - `StartHand`
  - `PlayerMove`
  - `Heartbeat`
  - `Reconnect`
  - `ChatMessage`
- ServerEvent:
  - `Joined`
  - `RoomSnapshot`
  - `Error`
  - `ServerNotice`
  - `HandResult` 通过 `RoomSnapshot.last_hand_result` 暴露

关键字段要求：

- 每个服务端事件包含 `event_id`。
- 客户端请求包含 `request_id`。
- 房间快照包含 `phase`、`seats`、`board`、`pot`、`current_bet`、`min_raise`、`dealer_seat`、`active_seat`、`hero_cards`、`current_hand_id`、`auto_start_countdown_seconds`。

## 6. 客户端 UI/UX 要求

### 6.1 主界面

必须包含：

- 服务器地址输入框。
- 昵称输入框。
- 连接按钮。
- 测试对手按钮。
- 牌桌区、公共牌区、座位区、本人手牌区、右侧信息区。

### 6.2 等待阶段交互

- 未入座时显示空位按钮。
- 入座后显示“准备/取消准备”和“离座”按钮。
- 未轮到自己时所有行动按钮禁用。
- 倒计时开始后桌面顶部显示“X 秒后开局”。

### 6.3 对局阶段交互

- 当前行动位要有明显高亮。
- 客户端按钮可用性与合法动作保持一致。
- 本人手牌始终可见。
- 其他玩家不展示具体手牌内容。

### 6.4 结果反馈

- 若存在 `last_hand_result`，侧边栏优先展示上一手赢家、手局 ID、筹码变化。
- 若不存在 `last_hand_result`，侧边栏展示最近日志。
- 本地日志路径可见，便于调试。

## 7. 非功能要求

- 服务端规则计算必须是权威来源。
- 客户端异常输入不能破坏房间状态。
- 自动化测试应能在本地无图形环境下执行客户端交互测试。
- 同一手牌前后总筹码守恒。

## 8. 自动化验收标准

本阶段完成后，以下命令应通过：

```powershell
python tools\check_rules.py
python -m unittest discover -s tests -v
python -m compileall server client shared tools tests
```

至少应覆盖：

- 服务端牌型评估。
- 服务端主池/边池结算。
- 房间从开局到结算的完整状态推进。
- 客户端按钮启用/禁用逻辑。
- 客户端动作派发。
- 客户端处理结算结果展示。

## 9. 后续迭代建议

以下能力建议留在下一阶段，而不是写成本阶段已完成：

- 重连后自动恢复座位与手牌的完整 UX。
- 行动倒计时和超时自动操作。
- 聊天可视化和消息气泡。
- 更丰富的加注输入方式和筹码动画。
- 多房间与大厅。
