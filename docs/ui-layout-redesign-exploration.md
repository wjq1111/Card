# 客户端 UI 布局重设计探索

## 1. 目标

为当前 `pygame` 客户端定义一套更清晰的桌面端布局方案，优先解决：

1. 牌桌主视觉不够聚焦
2. 房间信息、成员信息、动作区混在一起
3. 座位操作按钮与真实座位区域割裂
4. 后续如果要继续迭代 UI，缺少一套“布局规格语言”

这份文档先做探索，不直接约束实现细节。

## 2. 现状摘要

当前房间页主要结构来自 [client/main.py](/E:/MyGames/TexasHoldemOnline/client/main.py:459)：

1. 顶部左侧显示房间 ID、房主、状态
2. 中间是椭圆牌桌
3. 右侧是固定“房间信息”长侧栏
4. 底部左侧是一排 `座位 1..N` 按钮
5. 底部右侧是一排 `弃牌/过牌/跟注/加注/全下` 按钮

它能工作，但存在几个布局问题：

1. 座位卡片已经画在牌桌周围，但底部又有一排“座位按钮”，形成重复入口
2. 右侧栏过长，成员区、结果区、日志区都挤在一起，阅读负担偏大
3. 顶部状态、桌面状态、侧栏信息都在讲“同一局”的信息，信息分散
4. 玩家真正高频操作只有“行动按钮”和“轮到谁”，这些信息没有成为第一优先级

## 3. 重设计原则

结合当前德州桌面玩法，我建议遵循这几个规则：

1. 牌桌中央永远是主舞台，公共牌、底池、当前轮次必须一眼看到
2. 高频信息常驻，低频信息折叠
3. 玩家自己的信息固定在下沿中心，不和其他座位抢注意力
4. 所有“全局信息”收束到一个窄状态带，不要散落在多个角落
5. “座位交互”尽量贴着座位本体发生，不再额外做一整排独立座位按钮

### 4.2 信息密度解释

1. 顶栏只放“房间级别摘要”和“退出类按钮”
2. 中央只放底池、阶段、公共牌、发牌/结算反馈
3. 右侧栏压缩成“迷你侧栏”，只保留本局关键摘要，不再承载完整成员清单
4. 自己的状态和动作区合并到底部主控条，形成明确的“Hero HUD”

## 5. 分区建议

### A. Top Status Bar

用途：

1. 房间名 / 房间号
2. 当前局阶段 `WAITING / PREFLOP / FLOP / TURN / RIVER / SHOWDOWN`
3. 底池摘要
4. 倒计时
5. 离开房间、设置

设计约束：

1. 高度建议 `56-72px`
2. 不要放成员列表
3. 不要放整排大按钮

### B. Table Core

用途：

1. 公共牌
2. 当前底池
3. 当前轮次
4. 最近一次关键事件动画，例如“Seat 4 raises to 200”

设计约束：

1. 保证桌面中心大块留白
2. 公共牌永远居中
3. 不让日志和说明文字压到桌面中央

### C. Seat Ring

用途：

1. 显示 6 个座位
2. 每个座位包含名字、筹码、状态徽标
3. 如果是空位，直接在座位卡片上展示“点击入座”

设计约束：

1. 座位即交互点，不再额外复制成底部单独座位按钮带
2. 当前行动位高亮
3. 庄位、弃牌、全下、已准备都用小徽标表示

### D. Hero HUD

用途：

1. 玩家本人名称
2. 本人筹码
3. 当前应跟注金额
4. 手牌
5. 行动按钮
6. 加注滑条或档位器

设计约束：

1. 这是整个界面里最强的操作区
2. 放在底部中间，形成肌肉记忆
3. `Raise` 不建议只做固定金额，最好预留滑条/步进器

### E. Mini Side Panel

用途：

1. 房主 / 有效人数
2. 最近动作 3 条
3. 上一手赢家
4. 可折叠的成员入口

设计约束：

1. 宽度控制在 `220-260px`
2. 不再承担完整日志查看职责
3. 长日志和成员列表放抽屉层

## 6. 更适合你的“规范化描述语言”

你提到“有没有什么规范化的描述语言可以规定好什么地方在哪里”，这个方向是对的。对这个项目，我建议分三层理解：

### 方案 1：用“布局 DSL”描述区域

最适合你当前 `pygame` 项目的方式，是定义一份 JSON / YAML 布局规格，描述：

1. 区域名字
2. 锚点
3. 相对尺寸
4. 显隐条件
5. 层级和对齐方式

示例：

```yaml
screen: room
breakpoint: desktop
zones:
  - id: top_bar
    anchor: top
    x: 0
    y: 0
    w: 1.0
    h: 64
    layer: chrome

  - id: table_core
    anchor: center
    x: 0.22
    y: 0.16
    w: 0.52
    h: 0.58
    shape: oval
    layer: playfield

  - id: side_panel
    anchor: right
    x: 0.79
    y: 0.16
    w: 0.19
    h: 0.58
    collapsible: true
    layer: info

  - id: hero_hud
    anchor: bottom
    x: 0.14
    y: 0.82
    w: 0.72
    h: 96
    layer: control
```

这个方案的优点：

1. 很容易映射到 `pygame.Rect`
2. 很适合后续做不同分辨率适配
3. 可以把“布局”和“绘制逻辑”拆开

### 方案 2：用网格语言描述

如果你想更像 Web/CSS 一样表达布局，可以做一层简化版的 Grid 语法：

```yaml
grid:
  columns: [80, 1fr, 240]
  rows: [64, 1fr, 104]
areas:
  - id: top_bar
    area: "1 / 1 / 2 / 4"
  - id: table_core
    area: "2 / 2 / 3 / 3"
  - id: side_panel
    area: "2 / 3 / 3 / 4"
  - id: hero_hud
    area: "3 / 2 / 4 / 3"
```

这个方案优点是：

1. 表达紧凑
2. 对“区域排布”很清楚
3. 更接近成熟前端布局思维

缺点是：

1. 对圆桌和座位环绕这类非矩形布局不够直观
2. 座位仍然需要额外的环形定位算法

### 方案 3：用约束式语言描述

如果你想做得更工程化，可以定义约束：

```yaml
constraints:
  - seat_ring.center == table_core.center
  - hero_hud.bottom == screen.bottom - 16
  - side_panel.left == table_core.right + 20
  - top_bar.height == 64
  - table_core.width <= screen.width * 0.58
```

这更像 Auto Layout / Constraint Layout。

优点：

1. 适合复杂适配
2. 可维护性高

缺点：

1. 对你当前项目来说有点重
2. 实现成本明显高于 JSON 区域配置

## 7. 推荐结论

对于当前项目，我建议采用：

1. `区域 DSL + 少量环形座位算法`
2. 也就是“矩形区域用配置描述，6 个座位用程序按圆桌规则摆放”

原因是：

1. 你当前客户端就是 `pygame`，没有现成的 CSS/Grid 引擎
2. 牌桌 UI 最大的特殊性不是面板，而是“环桌座位”
3. 把座位也硬塞进通用 Grid，最后反而更绕

所以比较稳的方式是：

1. `top_bar / table_core / side_panel / hero_hud` 用 DSL
2. `seat_ring` 由 `table_core` 推导出 6 个锚点
3. 不同分辨率只换一套 `breakpoint` 配置

screen: room
breakpoints:

## 9. 这份探索对代码意味着什么

如果后面要正式改界面，我建议分三步：

1. 先把 [client/main.py](/E:/MyGames/TexasHoldemOnline/client/main.py:95) 里的布局计算抽到独立 `layout` 模块
2. 用一份 `layout_spec` 统一计算所有主要区域的 `pygame.Rect`
3. 再把座位、Hero HUD、侧栏拆成独立绘制函数或组件类
